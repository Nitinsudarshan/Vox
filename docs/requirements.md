# Vox — Functional & Non-Functional Requirements

## Functional Requirements

### 1. Audio Capture & Speech-to-Text (STT)
- **FR-1.1**: The system MUST support Push-to-Talk (PTT) capture via a configurable global hotkey and on-screen floating widget button.
- **FR-1.2**: The system MUST record audio from the default system microphone using WAV format (16kHz mono).
- **FR-1.3**: The system MUST transcribe recorded audio locally, with a Whisper model (`whisper-rs`) or — for dictation, when selected and installed — Parakeet TDT. No cloud STT is integrated (`docs/speech-providers.md`). When no dictation model is installed, the one the quality preset names is downloaded on first use and the pill says so; a meeting refuses to start (`MEETING_NO_SPEECH_MODEL`) rather than record audio that can never become a transcript. Neither path returns fake text.
- **FR-1.4 (Global Show/Hide Hotkey)**: The system MUST register a configurable OS-wide hotkey (default `Ctrl+Shift+Space`) that toggles the main window's visibility and focus from any other application.
- **FR-1.5 (Universal Dictation)**: The system MUST register a configurable OS-wide push-to-talk hotkey (default `Ctrl+Space`; hold to talk, or press twice with toggle-to-talk) that records audio while the always-on-top, non-focus-stealing pill shows it is listening; on release, the audio is transcribed and the resulting text is delivered into the field that had OS focus when recording started — not necessarily Vox's own window. No LLM runs unless the user has opted into a cleanup style, which may hold the text for at most five seconds (`docs/decisions.md` Decision 71).

### 2. Processing Pipeline
- **FR-2.1 (Meeting -> Kanban)**: The system MUST process meeting transcripts using an LLM prompt to extract structured action items containing `title`, `assignee`, `status` (`todo`, `in_progress`, `done`), `due_date`, and `description`. *(Deferred for the current desktop-first MVP phase — see `docs/decisions.md` Decision 33. Not built: there is no meeting-to-Kanban pipeline in the tree. Kanban cards are the TODOs surface's todos, and structured action-item extraction from meetings is `maybe_later.md` §16.)*
- **FR-2.2 (Scribble -> Structured Output)**: The system MUST process rambling audio scribbles using prompt templates to produce structured markdown notes containing summary, key decisions, and follow-ups. *(Built but unreachable: `PipelineEngine::process_scribble` implements this behind `start_capture` in `"scribble"` mode, and no surface starts that mode. A voice note promoted to a Scribble is enriched — title, summary, topics, entities — rather than restructured.)*
- **FR-2.3 (Trigger Phrase Engine)**: The system MUST classify transcribed text against user-defined trigger phrase mappings and route matching intents to specified actions (e.g. MCP Calendar entry, Local OS notification). *(Not built. Decision 35 deferred it; `docs/decisions.md` Decision 75 then removed the trigger engine, `triggers.json`, its settings tab and the MCP action stubs, none of which ever ran on a capture. No code in the tree implements this requirement. Spoken snippets, which expand a phrase into text, are a different feature and do ship.)*
- **FR-2.4 (Voice Chat / Vault Q&A)**: The system MUST support recording a spoken question, transcribing it, retrieving the most relevant vault notes as grounding context, and returning an LLM answer with the source note titles shown. Trigger-phrase matching MUST be skipped for this mode. If a local TTS engine is configured, the answer MUST additionally be synthesized as audio and returned for playback; if not configured, the feature degrades to text-only rather than failing the request. *(Deferred. The successor this requirement was resolved into — Talkback, `docs/decisions.md` Decision 47 — was itself removed; Decision 69 records that, and `native/src-tauri/src/tts/` is now the speech-synthesis interface with no provider behind it. "Pipeline and TTS code preserved" was true when written and is no longer.)*

### 2.5 Web Capture
- **FR-2.5.1 (Structured Web Capture)**: The system MUST be able to save the web page or conversation a user is looking at as structured text — conversation turns with role attribution, or document blocks (headings, paragraphs, lists, code, quotes, tables, images) — rather than as a screenshot. Semantic extraction is the primary mechanism; there is no screenshot or OCR path (`maybe_later.md` §7).
- **FR-2.5.2 (Provenance)**: Every capture MUST record `source_type`, `application`, `domain`, `url`, `page_title`, `captured_at`, `capture_type`, the extractor that produced it, and how the content was obtained. Provenance MUST NOT be mixed with semantic metadata (tags, topics, entities, summary), and MUST be derived by the backend from the URL rather than taken from the payload.
- **FR-2.5.3 (Honest Completeness)**: Every capture MUST state how much of the page it contains, and MUST NOT claim a full document without positive evidence. Limitations MUST be recorded in plain language on the artifact and surfaced in the UI.
- **FR-2.5.4 (Acquisition Before Interpretation)**: A capture MUST be persisted, with its raw source payload preserved, before any AI runs on it. A failed analysis MUST NOT lose or alter the captured content.
- **FR-2.5.5 (Least Privilege)**: Browser capture MUST use `activeTab` — access granted per-tab in response to an explicit in-browser gesture — and MUST NOT request standing access to all sites. Captured content MUST travel from the browser to Vox on the same machine, never through a third-party server.
- **FR-2.5.6 (Untrusted Input)**: Captured page content MUST be treated as untrusted: never executed, never stored or rendered as HTML, with control and text-direction characters removed and non-`http(s)` link targets dropped.
- **FR-2.5.7 (Re-capture)**: Capturing the same URL with unchanged content MUST NOT create a duplicate artifact. Capturing it with changed content MUST create a new version that references the one it supersedes.

### 3. Storage & Vault
- **FR-3.1 (Markdown Vault)**: The system MUST save all processed outputs as Obsidian-compatible Markdown files with YAML frontmatter headers in a local directory (`<base>/vault`, or the user's chosen Vault Directory Location — `docs/architecture.md` says how `<base>` is found).
- **FR-3.2 (Vector Store)**: The system MUST automatically generate text embeddings and store them in an embedded LanceDB vector database for semantic search over historical notes. *(Not built. Decided in `docs/decisions.md` Decision 6, but no embedding or vector store exists in the tree; retrieval ranks by keyword overlap (`VaultManager::search_notes`, `retrieval::`). See `docs/roadmap.md`.)*

### 4. Provider Abstraction
- **FR-4.1**: The backend MUST support swapping between local Ollama LLM models and cloud APIs (OpenAI, Gemini, Anthropic) via a unified settings configuration.

### 5. Application Surfaces
- **FR-5.1 (Native Desktop)**: The Windows app MUST render a responsive floating PTT widget, Kanban board viewer, voice chat panel, trigger phrase config UI, and provider/STT/TTS/hotkey settings. *(Deferred for the current phase — see Decisions 33–35 — and not in the tree: there is no Kanban board viewer (cards are listed on the TODOs surface), no voice chat panel (Decision 69), no trigger phrase config UI (Decision 75), and no TTS settings, because `tts/` has no provider behind it.)*
- **FR-5.2 (Browser Extension)**: The companion browser extension MUST allow capturing page text, structured turns, and metadata directly into the local vault via the secure loopback bridge.

### 6. Notifications & Windows Integration
- **FR-6.1 (Meeting Reminders)**: The system MUST present meeting reminders (upcoming, unrecorded, detected) in its own `meeting-reminder` window — created once and reused, never taking focus, kept out of screen shares, and carrying Record, Join and Snooze — because a desktop OS toast (`tauri_plugin_notification`) cannot carry action buttons. *(This reverses the toast-only requirement Decision 46 set; see `docs/decisions.md` Decision 63.)*

## Non-Functional Requirements

- **NFR-1 (Cost)**: Baseline operation MUST require $0 recurring cloud cost (local-first).
- **NFR-2 (Performance)**: Audio capture start latency MUST be <100ms. Local transcription and processing MUST execute asynchronously without blocking UI threads.
- **NFR-3 (Privacy & Security)**: Audio data and markdown vaults MUST remain stored locally by default. No cloud transmission occurs unless hybrid mode is enabled by the user. *(Two user choices also send data out without hybrid mode: a cloud LLM provider receives the text it is asked to process — a meeting transcript for a report, a dictation for an opt-in cleanup style — and a connected Google Calendar is read. Audio never leaves the machine; no cloud STT is integrated. Provider API keys are kept in the OS credential store, not in `settings.json` — `docs/decisions.md` Decision 73.)*
